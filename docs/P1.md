# 一  需求与总体设计

## 1. 项目业务目标与范围

### 1.1 业务目标

本项目建设一套**多模型 LLM 路由与执行平台**，核心目标如下：

1. **统一接入层**：为企业内部业务方（Slack IM、Web 控制台、第三方后端系统）提供统一的 LLM 调用入口，屏蔽底层多模型供应商（OpenAI、Anthropic、自托管 vLLM）的 API 差异与密钥复杂度
2. **智能路由决策**：基于查询类型、Token 规模、用户付费等级、模型能力、历史表现等多维度，将每一条请求自动分发到**综合最优**的模型后端，在质量 / 延迟 / 成本三者间取得可控平衡
3. **全链路可观测**：查询请求从接收、分类、路由、推理、响应到写入分析库的全链路，均具备结构化日志、Prometheus 指标、Grafana 可视化面板与可配置告警；支持后续按用户 / 模型 / 时间维度的成本归因、SLA 审计与问题排查。
4. **多租户治理**：支持 free / premium / enterprise 三级用户体系，具备每日/每小时请求配额、单次请求成本预算、延迟 SLA 目标等策略执行能力，保障付费用户体验、防止资源滥用。
5. **可扩展架构**：各模块（路由、推理、管线、监控、策略、质量、Adapter）独立可插拔，单服务启动时可根据配置开关按需加载；为后续 Adapter 微调、性能优化、Slack/Streamlit 集成留出清晰的扩展接口。

## 2. 用户与核心业务场景

### 2.1 用户角色定义

| 角色 | 描述 | 系统侧对应标识 |
|---|---|---|
| 终端用户（Free） | 免费体验用户，内部普通员工 | `UserTier.FREE` |
| 终端用户（Premium） | 付费增值用户，业务部门正式使用 | `UserTier.PREMIUM` |
| 终端用户（Enterprise） | 企业大客户，SLA 强保障、专属资源 | `UserTier.ENTERPRISE` |
| 平台运维工程师 | 部署、监控、排障、升级平台版本 | 通过 `/health`、`/admin`、CLI、Grafana 交互 |
| 平台研发工程师 | 迭代新功能、接入新模型、优化策略 | 通过源码、`/docs` OpenAPI、CLI 交互 |

### 2.2 核心业务场景（全链路，供 P1 设计接口时参考对齐）

1. **SC-01 普通 AI 查询**：用户通过 Slack 或控制台提交一句或长或短的自然语言请求，平台在数百毫秒内完成分类→路由→推理→返回响应，并记录完整日志与指标。
2. **SC-02 超长上下文摘要**：用户提交上万 Token 的文档 + 摘要指令，平台自动触发上下文压缩、路由到长上下文模型（Claude / Llama 70B），在用户可接受延迟内返回摘要。
3. **SC-03 代码生成/审查**：研发提交包含代码片段的请求，平台识别为 `code_generation` / `code_analysis` 类型，优先路由 GPT-4 Turbo 等高编码能力模型。
4. **SC-04 企业大客户 SLA 保障**：Enterprise 用户请求受 2s P95 延迟 SLA 与高配额保护；当首选模型抖动时自动降级到次优可用模型，全程有 SLO 违规告警。
5. **SC-05 平台运维日常巡检**：运维工程师通过 CLI `health` 命令 + Grafana 面板 + 告警通知，确认所有服务健康；通过 `/admin/reload-config` 在线调整路由权重或模型开关。
6. **SC-06 查询审计与成本分析**：财务/业务部门按月从 ClickHouse 拉取 query_logs、user_analytics 物化视图，按部门 / 用户 / 模型统计成本分布与使用趋势。
7. **SC-07 领域 Adapter 灰度发布**：算法团队训练完成某行业领域 LoRA Adapter，平台注册后按 5% → 20% → 100% 金丝雀放量，期间对比质量、成本、延迟指标，异常自动回滚。

P1 阶段本身不实现上述业务场景的逻辑代码，但 P1 产出的**Schema、Logger、Metrics、Config、API 接口签名**必须完整预留给上述场景，不得在后续阶段返工调整基础层。

## 5. 全局约束、设计原则、风险说明

### 5.1 全局约束（Cross-Cutting Constraints）

**C1：Python 版本与异步规范**

- 最低兼容 Python 3.9；代码语法不得使用 3.10+ 独有语法（match-case、dict \| dict、str | None 等可通过 `from __future__ import annotations` 或 typing.Union/Optional 兼容）。

**C2：配置来源与密钥安全**
- 所有 API Key / 令牌**必须**通过环境变量注入，代码中通过 `os.getenv("NAME")` 读取；禁止在 config.yaml、源码、测试用例中出现明文密钥。
- config.yaml 中凡是涉及密钥的字段，一律命名为 `xxx_env`（例如 `api_key_env: OPENAI_API_KEY`），存储变量名而非值本身。

**C3：跨模块数据传递**

- 跨模块参数传递**必须**使用 `src/utils/schema.py` 中定义的 Pydantic 模型；禁止在函数签名中使用 Dict[str, Any] 传核心业务数据（仅允许 metadata / labels 等极弱约束字段）

**C4：日志与指标可分级关闭**

- 任一模块的 stdout / file 日志输出都必须受 `logging.level` 控制；
- Prometheus 的可选集成（prometheus-client 未安装时）必须优雅降级，不得导致主服务启动失败。

**C5：可选组件零启动依赖**

- Kafka、ClickHouse、Redis、Prometheus Server、Grafana、Slack SDK 全部属于可选组件；P1 阶段服务启动流程中若对应 config.enabled=false 或依赖缺失，必须静默跳过，**不得阻塞 `/health` 端点可用**。

### 5.2 设计原则（Design Principles）

**DP1：约定优于配置（Convention over Configuration）**

- 目录结构、文件命名、类命名、指标命名全部有约定（见 4.2 与 P1 各任务细则）；
- 对约定的偏离必须显式写在 config.yaml 中，而非散落在各模块 `if/else`。

**DP2：小接口大实现（Simple Interface, Robust Implementation）**
- 每个底座模块对外暴露的公开 API 不超过 5 个函数/方法：
  - Logger：setup_logging() + get_logger(name)
  - Config：_load_config()（内部）+ 默认值回填
  - Metrics：四类 xxxMetrics 类实例化 → 直接访问属性
  - Schema：纯数据类，无方法（除 @validator）
  - Setup：setup_project_environment() 一个入口
  - CLI：四个子命令 start / setup / health / deploy

**DP3：失败可降级，启动不崩溃（Fail-Open for Infrastructure）**
- Logger 初始化失败 → 降级到 print；
- Prometheus 包不存在 → 暴露空指标，端点仍可用；
- Config 中缺 section → 自动注入默认值（main.py _load_config）。

**DP4：可观测优先（Observability First）**

- 即使 P1 阶段没有业务逻辑，`/health`、`/status`、`/metrics`（若启用）、`/admin/services` 四个端点必须完整实现；
- 所有跨模块 Pydantic 模型一律带 `timestamp`、`request_id` 等可追踪字段。

# 二  P1 阶段：项目底座与基础框架

## 1. P1 阶段里程碑目标

**M1：结构完整性**

- 项目根目录下按约定生成全部目录与模板文件；任何缺少的目录都能通过 `python main.py setup` 一键补齐。

**M2：服务可启动性**

- 不依赖 Kafka / ClickHouse / Redis / Prometheus Server / GPU / 模型权重 / 任何外部 API Key，在**全新 Python 3.11 环境**中仅执行 `pip install -r requirements.txt` → `python main.py start` 后：
  - 进程不崩溃退出（除非端口占用）；
  - `http://localhost:8080/health` 返回 HTTP 200，JSON body 中 `status == "healthy"`；
  - `http://localhost:8080/docs` 可访问 Swagger UI，列出所有基础端点。

**M3：接口规范性**
- 所有后续阶段（P2~P7）需要用到的**基础层对象**（Schema 模型、Logger 工厂、Metrics 类实例、CLI 命令、Config 加载机制）在 P1 结束时**全部就位**，后续阶段尽量不再修改其命名/字段签名

**M4：可运维性**
- CLI 四件套 `setup` / `start` / `health` / `deploy` 命令全部存在且可执行（`deploy` 允许在 P1 输出 "stub" 行为或空目录结构，实际生成留 P5）；
- `/admin/services` 能返回当前加载的服务列表与计数；
- `/admin/reload-config` 能重新加载并合并默认值。

## 3. P1 详细开发任务清单

### 任务 3.1：目录工程脚手架（part0_setup.py）

**对应文件与类**：

- 核心类：ProjectSetup（文件 `src/llm_router_part0_setup.py`）
- 入口函数：`setup_project_environment()`（同文件末尾）
- CLI 挂接：main.py 中 `@cli.command() setup`

**实现要点**：
1. **目录创建（_create_directories）**
   - 列表来源于 `ProjectSetup.required_dirs`，共 17 个目录：`config`、`data/queries`、`data/processed/routed`、`docker`、`.github/workflows`、`flink`、`kafka`、`clickhouse/data`、`monitoring/grafana`、`slack/credentials`、`streamlit_ui`、`logs`、`src/models`、`src/utils`、`tests`。
   - 统一使用 `Path.mkdir(parents=True, exist_ok=True)`，重复执行无副作用。
   - 对 Python 包目录（`src`、`src/models`、`src/utils`、`tests`）额外创建空的 `__init__.py` 文件（Path.touch）

2. **模板文件生成（_create_files）**
   - 字典 `required_files` 存储 10 份模板：
     - `.gitignore`：完整 Python 通用忽略 + LLM Router 专属（logs/、模型权重、.env 系列、clickhouse/data、docker/volumes/ 等）；
     - `README.md`：项目说明 Markdown 模板（P1 不必完美，允许后续替换）；
     - `requirements.txt` 与 `docker/requirements.txt`：见 §3.1 技术栈；
     - `kafka/topics.json`：4 个 Topic（queries/responses/metrics/errors）分区数/副本/保留时长/gzip 压缩配置；
     - `clickhouse/schema.sql`：4 张表（query_logs / system_metrics / model_performance / user_analytics）+ hourly_metrics 物化视图 + 3 条 BloomFilter 索引；
     - `monitoring/prometheus.yml`：7 个 scrape job（api/inference/vllm/kafka-exporter/clickhouse-exporter/node-exporter）+ alert_rules 引用 + alertmanager 目标；
     - `monitoring/grafana/dashboard.json`：3 个初始面板（RPS / P95 延迟 / 模型分布饼图）+ 时间窗口与刷新配置；
     - `streamlit_ui/config.toml`：暗黑主题配色（#FF6B6B 主色 / #0E1117 背景）+ 8501 端口 + CORS/XSRF 关闭（内网使用场景）；
     - `.github/workflows/ci.yml`：test / security-scan / docker-build / deploy 四 Job，含 Service 容器、pip 缓存、Buildx、多环境部署占位。
   - 写入策略：不存在则写入，已存在则跳过并 debug 日志记录。

3. **Python 环境安装（_setup_python_environment）**
   - 若 `<project_root>/venv` 目录不存在：`sys.executable -m venv venv` 创建虚拟环境；
   - 调用 venv 内的 pip（POSIX 下 `venv/bin/pip`）执行 `install -r requirements.txt`；
   - 本步骤允许耗时较长，期间通过 logger 输出进度。

4. **环境校验（_validate_environment + _validate_config）**
   - 目录检查：遍历 required_dirs，缺失则抛出 FileNotFoundError；
   - 关键文件检查：`config/config.yaml` 与 `requirements.txt` 必须存在；
   - 配置结构检查：config.yaml 中 api / router / inference / kafka / monitoring 五大 section 至少作为空 key 存在（若不存在，由 main.py 加载时补默认值；此处仅校验文件格式合法，yaml.safe_load 不抛异常）。

5. **公开入口函数**
   - `setup_project_environment()` 顺序：setup_logging → 实例化 ProjectSetup → setup_project_environment() → 返回；供 `main.py setup` CLI 调用。

### 任务 3.2：Pydantic 统一数据模型层（src/utils/schema.py）

**对应文件与类**：

- 文件：src/utils/schema.py
- 枚举：`UserTier`、`QueryType`、`AttachmentType`
- 模型类：`Attachment`、`QueryRequest`、`InferenceResponse`、`RoutingDecision`、`ModelSelection`、`ModelConfig`、`SystemMetric`、`UserSession`（附加）

**实现要点**：

1. **枚举层（str, Enum）**
   - `UserTier`：FREE="free" / PREMIUM="premium" / ENTERPRISE="enterprise"（注意值全小写，方便与 HTTP JSON 交互）；
   - `QueryType`：13 种，覆盖 GENERAL, CODE_GENERATION, CODE_ANALYSIS, ANALYSIS, SUMMARIZATION, CREATIVE_WRITING, BRAINSTORMING, PLANNING, QUESTION_ANSWERING, TRANSLATION, MATH, REASONING；
   - `AttachmentType`：FILE / IMAGE / DOCUMENT / AUDIO。

2. **Attachment 附件模型**
   - 字段：id（UUID 默认工厂）、name、type、size_bytes、mime_type、url（可选）、content（bytes 可选）；
   - `@validator('size_bytes')`：> 0 且 ≤ 100_000_000（100MB 上限）。

3. **QueryRequest 核心入参模型（关键，后续所有路由/推理代码都依赖它）**
   - 必填：`query: str`（min=1, max=50000）、`user_id: str`（min=1）；
   - 核心字段（带默认）：`user_tier=UserTier.FREE`、`request_id`（UUID 工厂）、`timestamp`（datetime.now 工厂）；
   - 可选设置：`context: str | None`（max=100000）、`max_tokens=512`（1~8192）、`temperature=0.7`（0.0~2.0）、`priority=1`（1~5）；
   - 附件：`attachments: List[Attachment] = []`，@validator 限制 ≤ 10 个；
   - 元数据：`session_id`、`conversation_id`、`metadata: Dict[str, Any] = {}`；
   - `@validator('query')`：去首尾空白后非空，否则抛 ValueError("Query cannot be empty or whitespace only")。

4. **InferenceResponse 核心出参模型**
   - 必填：`response_text`、`model_name`、`provider`；
   - Token：`token_count_input` / `token_count_output` / `total_tokens`（三者均 ≥ 0；`@validator('total_tokens', always=True)` 自动计算 input+output 若未传）；
   - 性能：`latency_ms`（≥ 0）、`tokens_per_second`（≥ 0.0）；
   - 成本：`cost_usd`（≥ 0.0）；
   - 系统标志：`cached=False`、`compressed_context=False`；
   - 质量（预留）：`quality_score`、`safety_score` 可选，0.0~1.0；
   - 错误：`error: str | None`、`finish_reason="stop"`；
   - 时间戳：`timestamp` datetime.now 工厂。

5. **路由层核心模型**
   - `RoutingDecision`：selected_model（必填 min_length=1）、query_type（QueryType）、routing_reason（必填 min_length=1）；metrics（token_count / estimated_cost / routing_time_ms / confidence 0.0~1.0）；timestamp 工厂；fallback_models 列表；routing_strategy 默认 "intelligent"；user_tier 默认 FREE。
   - `ModelSelection`：路由内部中间对象，model_name + confidence 0~1 + reason（均必填）。

6. **ModelConfig 模型配置模型**
   - 必填：name、provider、max_tokens（≥1）、cost_per_token（≥0.0）、priority（≥1）、capabilities（非空列表）；
   - 可选：model_path、gpu_memory_gb（≥1，int）、api_key_env；
   - `@validator('capabilities')`：逐项检查必须在 valid_capabilities 集合={reasoning, coding, analysis, writing, creative, general, math, translation} 内。

7. **SystemMetric 系统指标 + UserSession 预留**
   - SystemMetric：name（必填，必须 `alphanumeric + _ + .` 构成，@validator 正则校验）、value、timestamp 工厂、labels Dict[str,str]、unit 可选；
   - UserSession：session_id UUID、user_id、user_tier、start_time 工厂（P1 仅定义，供后续会话功能复用）。

**核心约束**：
- 所有枚举值全小写；
- 任何涉及数量的数值字段（token、cost、latency、priority、size_bytes）必须 ≥ 0；
- 所有 @validator 中禁止访问网络、禁止 IO；纯逻辑校验；
- 不允许在 schema.py 中 import 任何业务模块（logger / metrics / router 等都不行）。

### 任务 3.3：日志体系（src/utils/logger.py）

**对应文件与函数**：
- 文件：src/utils/logger.py
- 公开函数：`setup_logging(log_level, log_file, console_output, structured_logs)` 与 `get_logger(name: str) -> logging.Logger`

**实现要点**：
1. **setup_logging 参数默认值与兼容策略**
   - 所有参数可选；若调用方不传，则等价于：
     - log_level = "INFO"
     - log_file = "logs/llm_router.log"
     - console_output = True
     - structured_logs = True
   - 函数执行前需确保 `<log_file 所在目录>` 存在（Path.parent.mkdir）。

2. **根 Logger 配置**
   - 获取 root logger 或专用 logger name（推荐统一命名空间 `"llm_router"`，避免污染第三方库日志格式）；
   - 级别：`getattr(logging, log_level.upper(), logging.INFO)`；
   - 关闭 propagate（若使用命名空间 logger）以免重复输出。

3. **Console Handler（开发观察）**
   - 当 `console_output=True`：StreamHandler(sys.stdout) + 级别 DEBUG；
   - Formatter 人类可读：`"%(asctime)s - %(name)s - %(levelname)s - %(message)s"`。

4. **File Handler（生产留存）**
   - 始终开启（除非 structured_logs 启用 JSON 单独通道）；使用 `logging.handlers.RotatingFileHandler`；
   - 参数来源：若 main.py 中 config.logging.max_bytes / backup_count 存在则用之，否则默认 max_bytes=10MB, backup_count=5；
   - 日志级别 INFO，Formatter 与 Console 一致。

5. **可选 JSON 结构化日志（structured_logs=True 时）**
   - 引入 python-json-logger 的 `JsonFormatter` 或 structlog processor；
   - 为 File Handler 绑定第二个 JSON 输出文件（`<log_file>.jsonl`）或与原文件共用但使用 JSON 行格式；
   - JSON 字段至少包含：`asctime / name / levelname / message / process / thread / module / lineno`。

6. **get_logger 工厂**
   - 输入 name（建议调用方传 `__name__`）；
   - 返回 `logging.getLogger(f"llm_router.{name}")`；
   - 若 setup_logging 从未调用（防御性代码），返回前确保至少有一个 NullHandler，避免 "No handler found" 警告。

7. **异常兜底**
   - 所有 handler 创建、目录创建若出错，捕获后降级：至少保留一个 StreamHandler(level=WARNING) 让服务不崩。

**核心约束**：
- 日志输出中不得出现明文 API Key、用户输入敏感原文（若后续需打印需脱敏，在业务层做，不在 logger.py 做）；
- 所有 logging 相关配置仅在 setup_logging() 内集中完成；其他模块禁止调用 `logging.basicConfig` 或直接 addHandler。
