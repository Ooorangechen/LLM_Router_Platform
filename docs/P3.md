# I. Inheritance and Change Description

## 1. Inheritance: Reusing P1 and P2 Infrastructure Layer and Business Layer

This phase **fully reuses** the following infrastructure and business capabilities defined in the P1 and P2 design documents:

1. **Directory Engineering Structure**: Project root directory, config/, src/, src/utils/, src/models/, logs/, data/, tests/, kafka/, clickhouse/, monitoring/ — all follow P1 conventions;
2. **Unified Schema Model Layer** (src/utils/schema.py): All enumerations and Pydantic models such as `UserTier`, `QueryType`, `AttachmentType`, `QueryRequest`, `InferenceResponse`, `RoutingDecision`, `ModelConfig`, `SystemMetric`, `UserSession`, etc. — fields and @validator rules **shall not be changed in any way**; P3 only adds dedicated Schema for Kafka message entries in separate files without modifying existing Schema;
3. **Unified Logging System** (src/utils/logger.py): `setup_logging()` four parameters + `get_logger(name)` factory; all new P3 modules obtain named Logger via `get_logger("pipeline")` / `get_logger("kafka")` / `get_logger("clickhouse")`;
4. **Metrics Framework** (src/utils/metrics.py): Four category instances `SYSTEM_METRICS`, `ROUTER_METRICS`, `INFERENCE_METRICS`, `PIPELINE_METRICS`; P3 only adds Kafka/ClickHouse related Counter/Gauge/Histogram under `PIPELINE_METRICS` without modifying existing metric signatures;
5. **Configuration Management System** (`config/config.yaml` is the complete baseline; `main.py` deep-merges an optional custom override): All section names and default values already in P1/P2 remain unchanged; **P3 adds three top-level sections: kafka / clickhouse / pipeline**;
6. **FastAPI Base** (main.py LLMRouterPlatform class skeleton + CORS/exception/lifecycle): No new external business endpoints are added; only a PipelineManager is optionally created during startup lifecycle according to the `pipeline.enabled` switch; existing endpoints `/health`, `/status`, `/admin/*`, `POST /route` are not modified;
7. **Core Business Chain** (P2 ModelRouter + InferenceEngine + `POST /route`): P3 is connected to the pipeline via **decorator/Hook callback** approach without modifying internal logic code of routing and inference modules; when `pipeline.enabled=False`, the main P2 chain behavior is completely consistent with P2 acceptance criteria;

## 2. P3 Phase New Business Scope

This phase delivers the **asynchronous data flow pipeline and persistence layer**, with the core objective of decoupling all runtime data generated by the P2 main chain through Kafka and then writing it to ClickHouse, providing a structured data source for P4 monitoring dashboards, P5 cost auditing and quality analysis.

The new business capabilities added in this phase are as follows:

| Capability Item | Description |
|---|---|
| Kafka Topic Definition and Metadata | 4 business topics (queries/responses/metrics/errors) + 1 dead letter topic, including partition count, replication factor, retention policy configuration |
| Kafka Producer Manager | Asynchronous sending, batch buffering, gzip compression, 3 retries, send callback instrumentation, failure degradation logging |
| Kafka Consumer Engine | Consumer group management, manual Offset commit, batch polling, distribution to write processors by Topic |
| ClickHouse Table Structure Design | 4 business tables (MergeTree/ReplacingMergeTree/SummingMergeTree) + 1 materialized view, including partitions, TTL, BloomFilter indexes |
| ClickHouse Client Encapsulation | Connection pool, batch INSERT (JSONEachRow format), exponential backoff retry, dead letter queue disk persistence |
| Runtime Instrumentation Hook | Publishes 4 types of messages to Kafka **asynchronously and non-blocking** after the `POST /route` response; main chain latency is not affected by writes |
| Flink Job Framework (Optional) | High-level aggregation pipeline skeleton: Kafka Source → 1-hour tumbling window → ClickHouse Sink, disabled by default |
| Pipeline Master Switch | Controlled by `pipeline.enabled`; when turned off, Kafka/ClickHouse initialization and sending are completely skipped, running with zero dependencies |

At the end of P3, with the switch enabled, the E2E from HTTP request to structured database storage via Kafka + ClickHouse can be completed; with the switch disabled, all P2 MVP acceptance scripts pass as-is (zero regression).

# II. P3 Phase Development Subjects

## 1. P3 Phase Milestone Objectives

### M1: Pipeline Toggleable and Non-Regressive
- Start service with `pipeline.enabled=False`: All 7 P2 acceptance items (including `POST /route` E2E, cache hit, compression trigger, Fallback) PASS, and no "kafka" / "clickhouse" / "pipeline" related warnings appear in logs;

- After starting single-node Kafka (or Mock) locally, send 1 `POST /route` request; each of the 4 Topics (llm-queries / llm-responses / llm-metrics / llm-errors) in Kafka has 1 corresponding message, and the query_id fields are completely consistent;

- After starting ClickHouse locally, execute schema.sql to create tables successfully;
- After continuously sending 50 `POST /route` requests, query_logs table row count = 50, each row query_id is unique; system_metrics table has at least 50*N (N=metric type) rows;
- Aggregation rows for the corresponding hour can be seen in the materialized view hourly_metrics (request_count >= 50).

### M4: Dead Letter and Fault Tolerance
- Manually shut down the ClickHouse port and send 10 requests: 10 messages enter the Kafka DLQ Topic (llm-dead-letter) or local `data/dlq/*.jsonl` files; main chain HTTP 200 without exceptions;
- After restarting ClickHouse, executing the `python main.py replay-dlq` CLI command can rewrite dead letters to ClickHouse, and query_logs row count is supplemented after the rewrite.

### M5: PIPELINE_METRICS Observable
- The following new PIPELINE_METRICS indicators appear in the `/metrics` endpoint, and the count increments after calling:
  - `pipeline_kafka_produce_total{topic,status}` (success/failure)
  - `pipeline_clickhouse_write_total{table,status}` (success/retry/failure)
  - `pipeline_clickhouse_write_latency_seconds{table}` Histogram
  - `pipeline_dead_letter_total{source}` Counter

### Task 3.3: Kafka Producer Manager KafkaProducerManager

**File**: `src/llm_router_part3_pipeline.py` (after Schema, core class)

**Classes and Methods**:
- Class: `KafkaProducerManager(config: Dict[str, Any])`
  - Attributes: `self.enabled`, `self.bootstrap_servers`, `self.producer` (aiokafka.AIOKafkaProducer or confluent_kafka.Producer), `self.topics` (read from kafka/topics.json or overridden by config.kafka.topics)
  - `async initialize()`
  - `async _ensure_topics_exist()` (optional: attempts to create non-existent Topics, fails with warning without throwing)
  - `async produce(topic: str, key: Optional[str], value: BaseModel, headers: Optional[Dict[str, str]] = None) -> bool`
  - `async produce_batch(records: List[Tuple[str, Optional[str], BaseModel]]) -> Tuple[int, int]` (success_count, failure_count)
  - `async flush()`
  - `async shutdown()`

**Producer Configuration (Must hardcode default values + config.yaml overridable)**:
| Configuration Item | Default Value | config.yaml Path |
|---|---|---|
| acks | "all" | kafka.producer.acks |
| retries | 3 | kafka.producer.retries |
| batch_size | 16384 | kafka.producer.batch_size |
| linger_ms | 5 | kafka.producer.linger_ms |
| compression_type | "gzip" | kafka.producer.compression_type |
| request_timeout_ms | 30000 | kafka.producer.request_timeout_ms |
| max_in_flight_requests_per_connection | 5 | kafka.producer.max_in_flight (reserved for compatible backends; current aiokafka does not expose this constructor option) |
| enable_idempotence | true | kafka.producer.enable_idempotence |

**Implementation Key Points**:
1. **Initialization Degradation**: `initialize()` internally `try` to connect Kafka (`@retry` 3 times), all fail → `self.enabled=False` + `logger.warning("Kafka producer disabled: connection failed")`, **does not throw exceptions upward**, service starts normally;
2. **produce asynchronous sending**:
   - value uniformly `model.model_dump_json().encode("utf-8")`;
   - key uses `str(query_id)` or hash(user_id) to ensure the same query_id routes to the same partition;
   - aiokafka uses `await producer.send_and_wait(topic, value, key=key, headers=headers)`; on success → `PIPELINE_METRICS.kafka_produce_total.labels(topic=topic, status="success").inc()`;
   - Send failure (timeout, exception) → after catch, `PIPELINE_METRICS.kafka_produce_total.labels(topic=topic, status="failure").inc()` + `logger.error("Kafka produce failed ...")`, **does not throw exception to caller**; returns False;
3. **Message headers**: Each message carries `{"query_id": str(...), "produced_at": datetime.utcnow().isoformat(), "schema_version": "1.0"}`;
4. **Completely disabled mode**: If `pipeline.enabled=False`, main.py does not instantiate KafkaProducerManager at all; if `pipeline.enabled=True` but Kafka cannot connect, instantiate but with enabled=False, produce() directly returns True (no-op success), does not block the main chain.

**Core Constraints**:
- produce/produce_batch **never throws exceptions**, at most returns False or (N_fail, 0);
- The main chain `POST /route` must call produce using `asyncio.create_task(...)` for background sending, **do not await**, to ensure HTTP response latency is not affected by Kafka fluctuations;
- Sending order is not guaranteed (queries/responses/metrics can enter Kafka out of order); the ClickHouse side merges by time when using query_id for association analysis.

**Class B: `ClickHouseWriter(config)`**
  - Attributes: `self.enabled`, `self.client` (clickhouse_connect.Client or connection pool), `self.batch_size`, `self.retry_max`, `self._buffers: Dict[str, List[Dict]]` (buffer rows by table name), `self._dlq_local_path` (default `data/dlq/`)
  - `async initialize()`
  - `async _create_tables_if_not_exists()` (reads clickhouse/schema.sql and executes; failure warning)
  - `async buffer_write(table: str, row: Dict)`: single row buffer, flush when batch_size is reached
  - `async flush_table(table: str) -> Tuple[int, int]`: returns (wrote, failed)
  - `async flush_all()`
  - `async _execute_insert(table: str, rows: List[Dict]) -> None`: INSERT ... FORMAT JSONEachRow
  - `async _write_to_dlq(table: str, rows: List[Dict], reason: str)`
  - `async replay_dlq(since: Optional[datetime] = None) -> Tuple[int, int]`
  - `async shutdown()`

**Implementation Key Points (Consumer Loop)**:
1. Use `async for msg in consumer:` in `_consume_loop`, group by topic after batch polling;
2. Each batch (500 entries or timeout) calls `_handle_message` → ClickHouseWriter.buffer_write → flush_table after reaching 500 entries;
3. **Manual Offset Commit**: Only after flush_table for the batch messages returns success, execute `await consumer.commit()`; if write fails, do not commit and enter DLQ;
4. Mapping from Topic to ClickHouse table:
   | Kafka Topic | ClickHouse Table |
   |---|---|
   | llm-queries | query_logs (INSERT) |
   | llm-responses | query_logs (UPDATE with query_id as primary key, or directly INSERT new rows merged by ReplacingMergeTree; recommended to use ReplacingMergeTree for query_logs or put Responses into a separate table) |
   | llm-metrics | system_metrics |
   | llm-errors | (Write directly to system_metrics or separate error table; if error_logs table is not created in schema.sql, uniformly write to system_metrics with metric_name="error_event") |
5. **Consumption Failure Handling**: Any step exception → produce the original message as-is to the `llm-dead-letter` Topic, while local JSONL disk persistence for double insurance.

**Implementation Key Points (ClickHouseWriter)**:
1. **Connection Pool**: clickhouse_connect client uses HTTP protocol (port 8123) is sufficient, no need for Native TCP; configure max_connections=10;
2. **Batch Write SQL**: `INSERT INTO {table} FORMAT JSONEachRow`, rows pass list[dict];
3. **Retry Strategy**: `_execute_insert` failure → exponential backoff retry (backoff = 1s → 2s → 4s → 8s, up to 3 times), all failures → all rows enter DLQ;
4. **TTL and Partition**: See Task 3.5 for table creation statements;
5. **DLQ Disk Persistence**: `data/dlq/YYYYMMDD_HH.jsonl`, one JSON per line (including table, rows, reason, timestamp); `replay_dlq` scans jsonl within 7 days and re-executes _execute_insert, archive to `data/dlq/archived/` after success.

**Core Constraints**:
- ClickHouse write failure must not block the consumption loop (DLQ after failure → continue to next batch);
- enable_auto_commit must be False, strictly ensure **Offset is committed only after write success**;
- buffer_write / flush_table do not throw exceptions, at most return failure count and write DLQ.

### Task 3.5: ClickHouse Table Structure schema.sql + Materialized View

**File**: `clickhouse/schema.sql`

**Must strictly implement 4 tables + 1 materialized view**:

```sql
-- ============================================================
-- 1. query_logs: Query + Response merged detail table
--    MergeTree partitioned by month, TTL 90 days; BloomFilter index
-- ============================================================
CREATE TABLE IF NOT EXISTS query_logs
(
    query_id            UUID,
    user_id             String,
    user_tier           LowCardinality(String),
    query_text          String,
    query_type          LowCardinality(String),
    selected_model      LowCardinality(String),
    routing_strategy    LowCardinality(String),
    routing_confidence  Float32,
    token_count_input   UInt32,
    token_count_output  UInt32,
    total_tokens        UInt32,
    temperature         Float32,
    max_tokens          UInt32,
    has_context         UInt8,
    has_attachments     UInt8,
    provider            LowCardinality(String),
    response_text       String CODEC(ZSTD(1)),
    cost_usd            Decimal(18, 8),
    latency_ms          UInt32,
    routing_time_ms     UInt32,
    cached              UInt8,
    compressed_context  UInt8,
    status              LowCardinality(String),
    error               Nullable(String),
    request_received_at DateTime64(3, 'UTC'),
    response_completed_at DateTime64(3, 'UTC'),
    day                 Date MATERIALIZED toDate(request_received_at)
)
ENGINE = ReplacingMergeTree(response_completed_at)
PARTITION BY toYYYYMM(request_received_at)
ORDER BY (query_id, request_received_at)
PRIMARY KEY query_id
TTL request_received_at + INTERVAL 90 DAY
SETTINGS index_granularity = 8192;

-- BloomFilter index (optional: execute ALTER TABLE after table creation or inline directly)
ALTER TABLE query_logs ADD INDEX IF NOT EXISTS bf_user_id user_id TYPE bloom_filter GRANULARITY 1;
ALTER TABLE query_logs ADD INDEX IF NOT EXISTS bf_model   selected_model TYPE bloom_filter GRANULARITY 1;
ALTER TABLE query_logs ADD INDEX IF NOT EXISTS bf_status  status TYPE bloom_filter GRANULARITY 1;
ALTER TABLE query_logs MATERIALIZE INDEX IF EXISTS bf_user_id;
ALTER TABLE query_logs MATERIALIZE INDEX IF EXISTS bf_model;
ALTER TABLE query_logs MATERIALIZE INDEX IF EXISTS bf_status;

-- ============================================================
-- 2. system_metrics: Metric details
--    ReplacingMergeTree, partitioned by day, TTL 30 days
-- ============================================================
CREATE TABLE IF NOT EXISTS system_metrics
(
    timestamp    DateTime64(3, 'UTC'),
    service      LowCardinality(String),
    metric_name  LowCardinality(String),
    value        Float64,
    labels       Map(LowCardinality(String), String),
    day          Date MATERIALIZED toDate(timestamp)
)
ENGINE = ReplacingMergeTree(timestamp)
PARTITION BY toYYYYMMDD(timestamp)
ORDER BY (service, metric_name, labels, timestamp)
TTL timestamp + INTERVAL 30 DAY
SETTINGS index_granularity = 8192;

-- ============================================================
-- 3. model_performance: Model dimension aggregation table
--    ReplacingMergeTree, partitioned by month, TTL 60 days
--    Written by consumer engine or Flink job
-- ============================================================
CREATE TABLE IF NOT EXISTS model_performance
(
    day                 Date,
    model_name          LowCardinality(String),
    provider            LowCardinality(String),
    request_count       UInt64,
    success_count       UInt64,
    error_count         UInt64,
    total_tokens_input  UInt64,
    total_tokens_output UInt64,
    total_cost_usd      Decimal(32, 8),
    avg_latency_ms      Float64,
    p95_latency_ms      Float64,
    p99_latency_ms      Float64,
    cache_hit_count     UInt64,
    updated_at          DateTime64(3, 'UTC') DEFAULT now64()
)
ENGINE = ReplacingMergeTree(updated_at)
PARTITION BY toYYYYMM(day)
ORDER BY (day, model_name)
TTL day + INTERVAL 60 DAY
SETTINGS index_granularity = 8192;

-- ============================================================
-- 4. user_analytics: User dimension aggregation table
--    SummingMergeTree, partitioned by month, TTL 180 days
-- ============================================================
CREATE TABLE IF NOT EXISTS user_analytics
(
    day                 Date,
    user_id             String,
    user_tier           LowCardinality(String),
    request_count       UInt64,
    total_tokens_input  UInt64,
    total_tokens_output UInt64,
    total_cost_usd      Decimal(32, 8),
    error_count         UInt64,
    avg_latency_ms      Float64
)
ENGINE = SummingMergeTree((request_count, total_tokens_input, total_tokens_output, total_cost_usd, error_count))
PARTITION BY toYYYYMM(day)
ORDER BY (day, user_id, user_tier)
TTL day + INTERVAL 180 DAY
SETTINGS index_granularity = 8192;

-- ============================================================
-- 5. hourly_metrics Materialized View: Real-time aggregation by model dimension per hour
--    Automatically triggered when writing from query_logs
-- ============================================================
CREATE MATERIALIZED VIEW IF NOT EXISTS hourly_metrics
TO model_performance
AS
SELECT
    toDate(request_received_at)                                               AS day,
    selected_model                                                            AS model_name,
    any(provider)                                                             AS provider,
    count()                                                                   AS request_count,
    countIf(status = 'success')                                               AS success_count,
    countIf(status = 'error')                                                 AS error_count,
    sum(token_count_input)                                                    AS total_tokens_input,
    sum(token_count_output)                                                   AS total_tokens_output,
    sum(cost_usd)                                                             AS total_cost_usd,
    avg(latency_ms)                                                           AS avg_latency_ms,
    quantileExact(0.95)(latency_ms)                                           AS p95_latency_ms,
    quantileExact(0.99)(latency_ms)                                           AS p99_latency_ms,
    sum(cached)                                                               AS cache_hit_count,
    now64()                                                                   AS updated_at
FROM query_logs
WHERE request_received_at >= now() - INTERVAL 2 HOUR
GROUP BY
    toStartOfHour(request_received_at),
    toDate(request_received_at),
    selected_model
SETTINGS allow_experimental_analyzer = 1;
```

**Implementation Key Points**:
1. Table creation scripts are idempotent (`CREATE TABLE IF NOT EXISTS` / `ADD INDEX IF NOT EXISTS`), can be executed repeatedly;
2. Read this SQL file in ClickHouseWriter.initialize(), split by semicolon `;` then execute item by item, skip empty lines and comment lines (starting with `--`);
3. Materialized view hourly_metrics: enabled by default, continuously writes incrementally from query_logs to model_performance; latency is tolerable when write volume is small.

**Core Constraints**:
- All time columns uniformly use `DateTime64(3, 'UTC')`, usage of local timezone time is prohibited;
- Decimal type cost fields must not use Float (to avoid precision loss);
- TTL must be declared; unlimited table growth will cause disk overflow.

### Task 3.6: Flink Stream Processing Job Framework (Optional High-Level Pipeline)

**Files**:
- New `flink/job.py` (or `src/flink_job.py`, P3 is not required to actually run, only requires file existence + code skeleton can be imported without error)
- New `flink/requirements.txt` (Flink Python dependencies: apache-flink==1.18+)

**Classes and Methods**:
- Function: `build_streaming_job(kafka_bootstrap: str, kafka_topics: List[str], clickhouse_jdbc_url: str, env_config: Dict) -> "StreamExecutionEnvironment"`
  - Internal construction:
    1. Kafka Source: FlinkKafkaConsumer or KafkaSource, deserialize JSON to Row (query_id / model / cost / latency / event_time);
    2. WatermarkStrategy: forBoundedOutOfOrderness(Duration.ofSeconds(30)), based on query_logs.request_received_at;
    3. Window: TumblingEventTimeWindows.of(Time.hours(1)), keyBy(model_name);
    4. Aggregation: Count / Sum(tokens) / Sum(cost) / Avg(latency) / Quantile(latency, 0.95);
    5. ClickHouse Sink: JDBCSink or AsyncHttpSink, writes to model_performance table, upsert on (day, model_name);
- Function: `run_job(args)` (parse CLI parameters → build_streaming_job → `env.execute("LLM Router Analytics")`)
- Parallelism: Default `parallelism.default = 2`, `checkpointing.interval = 60000`, Exactly-once.

**Implementation Key Points**:
1. **P3 does not require Flink to actually run**: As long as the code structure exists and `import flink.job` does not report errors (or stub empty functions after try import apache_flink fails); the core data path uses the consumer engine + materialized view from Task 3.4;
2. Configuration: config.yaml adds `flink.enabled = False` (off by default), Flink-related items are not checked during P3 acceptance.

**Core Constraints**:
- When `pipeline.enabled=True`, Flink can run independently of the main service (separate process or YARN/K8s), not embedded within the FastAPI process;
- Flink job writes to model_performance with **consistent primary keys** as materialized view writes (ORDER BY day, model_name), automatically merged and overwritten by ReplacingMergeTree, repeated writes are idempotent.
