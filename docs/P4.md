# I. Inheritance and Changes Description

## 1. Inheritance: Reusing P1, P2, P3 Foundation and Business Layers

This phase **completely reuses** the infrastructure and business capabilities defined in the P1, P2, and P3 design documents:

1. **Directory Engineering Structure**: Project root, config/, src/, src/utils/, kafka/, clickhouse/, monitoring/, data/, logs/, tests/, scripts/ strictly follow the P1~P3 conventions;
2. **Unified Schema Model Layer** (src/utils/schema.py): Enumerations and Pydantic models such as `UserTier`, `QueryType`, `QueryRequest`, `InferenceResponse`, `RoutingDecision`, `ModelConfig`, `SystemMetric`, etc., **remain unchanged**; P4 only adds monitoring-specific Schemas such as AlertRule / AlertRecord / HealthStatus in a new file;
3. **Unified Logging System** (src/utils/logger.py): `setup_logging()` + `get_logger(name)` factory; newly added P4 modules obtain named Loggers via `get_logger("monitor")` / `get_logger("alert")` / `get_logger("health")`;
4. **Metrics Framework** (src/utils/metrics.py): Four metric category instances: `SYSTEM_METRICS` / `ROUTER_METRICS` / `INFERENCE_METRICS` / `PIPELINE_METRICS`; P4 **completes** the uninstantiated Counter/Gauge/Histogram fields on top of these four categories and adds three new containers: `RESOURCE_METRICS` / `ALERT_METRICS` / `HEALTH_METRICS`. Legacy metric names remain unchanged;
5. **Configuration Management System** (config/config.yaml + main.py _load_config default injection): All existing sections from P1~P3 retain their default values; P4 only adds a top-level `monitoring` section and fills in its default values in `main.py` `_load_config`;
6. **FastAPI Foundation** (main.py LLMRouterPlatform class skeleton): Only appends/enhances the return content and sub-service traversal logic of basic endpoints like `/health`, `/status`, `/metrics`, `/analytics`, **without modifying** the signature and main flow of the `POST /route` business endpoint;
7. **P2 Routing Inference MVP** (ModelRouter / InferenceEngine / `POST /route`): No internal changes; P4 reads directly via instrumentation already present in PIPELINE_METRICS + SYSTEM_METRICS;
8. **P3 Kafka+ClickHouse Data Pipeline** (KafkaProducerManager / KafkaConsumerEngine / ClickHouseWriter): P4 does not modify core pipeline logic, only declares two scrape jobs (external Exporter processes) `kafka-exporter` / `clickhouse-exporter` in monitoring/prometheus.yml, and adds an optional resource collector;
9. **Global Design Principles and Constraints** (P1 Doc §5): Hard constraints C1~C5, design principles DP1~DP4.

## 2. P4 Phase New Business Scope Summary

This phase delivers a **production-grade monitoring, observability, and alerting closed loop**, ensuring that after system deployment, health can be "observed in real-time, and anomalies can be heard."

The new business capabilities in this phase are as follows:

| Capability Item | Description |
|---|---|
| System Resource Collector | Background loop collecting CPU%, Memory%, Disk%, GPU Load + Memory, Network IO (Rx/Tx bytes), Process count, Uptime, writing to RESOURCE_METRICS Gauge |
| Complete Prometheus Metrics Export | All Metrics class instances fully equipped with Counter/Gauge/Histogram/Info/Enum; `/metrics` endpoint fully exposed; optional standalone Prometheus HTTP Server (separate port to prevent competition with business logic) |
| Prometheus Configuration File | 7 scrape jobs (llm-router-api / inference / vllm-server / kafka-exporter / clickhouse-exporter / node-exporter) + global scrape_interval + alert_rules.yml rule_files reference |
| Grafana Dashboard JSON | Request Rate RPS (Stat), P95 Response Latency (Stat), Success Rate (Stat), Cost/Hour (Stat), Model Usage Distribution Pie Chart, Latency Trend faceted by model × user_tier, Top N Error Rate Query + Global Grid Layout + 6h default time window + 30s auto_refresh |
| Alert Manager | AlertRule structure (name/condition/threshold/duration/severity/description), 4 default rules (High Error Rate 5% / High Latency P95 / Memory 90% / Disk 80%), Alert Deduplication (duration) + Suppression (same alert silent for N mins) + History log (ring buffer max 1000 items), Notification Processor Framework (Slack Webhook / Email / PagerDuty interface stub empty implementation) |
| Complete Health Check System | `/health` traverses all registered services (router/inference/pipeline/monitor/...) returning each sub-service's healthy/degraded + overall status; `/status` endpoint outputs resource metrics snapshot + routing mode + model list + pipeline status + active alerts count; `/analytics` returns RPS/Success Rate/P95 aggregated by model for past N minutes; CLI `python main.py health` prints human-readable status table |
| Master Monitoring Switch | Controlled by `monitoring.enabled`. When disabled, completely skips initialization of resource collector, alert manager, and standalone Prometheus Server; existing business + pipeline remain unaffected; `monitoring.alert_enabled` separately controls alert computation |

At the end of P4, with the monitoring switch enabled, production-grade "Three Pillars" observability can be completed via Prometheus + Grafana + Alert Manager; with the switch disabled, all P2 / P3 acceptance scripts PASS without modification.

### M4: Alert Rule Trigger + Notification + Deduplication + History
- After simulating fault scenarios (artificially setting error rate > 5%, or memory_percent ≥ 90), after the duration window expires, the alert manager exhibits:
  - `GET /admin/alerts/active` returns ≥ 1 active alert (name/severity/fired_at fields complete);
  - Reserved Slack Webhook notify method is invoked (mock count +1);
  - Repeating identical metric fluctuation 100 times within 1 second produces only 1 alert history record (deduplication active);
- `GET /admin/alerts/history` returns ≤ 1000 ring buffer records in reverse chronological order.

### M5: Complete Health Check System
- `/health` returns JSON `status=healthy/degraded/unhealthy` + `services` Dict, where each registered service (at least router/inference/pipeline/monitor/alert) contains three fields: status, last_check_at, message;
- `/status` returns fields: CPU%, Memory%, Disk%, routing mode, model count, pipeline.enabled, monitoring.enabled, active_alerts_count, uptime_seconds;
- `python main.py health` CLI command prints a color-coded table (or plain text table), exit code = 0 for healthy, 2 for degraded, 3 for unhealthy;
- `/analytics?window_minutes=5` returns aggregated values by model: model_name, request_count, success_rate, p95_latency_ms, avg_cost_usd.

### Task 3.1: System Resource Collector SystemResourceCollector

**File**: Add `src/llm_router_part4_monitor.py` (First half of file, Collector + Monitoring Schema)

**A. New Pydantic Models (First part of file)**:

1. **`ResourceSnapshot(BaseModel)`** (Resource Snapshot, returned directly by /status):
| Field Name | Type | Description |
|---|---|---|

| memory_percent | float | 0.0 ~ 100.0 |
| memory_used_bytes | int |  |
| memory_total_bytes | int |  |
| disk_percent | float | 0.0 ~ 100.0 |
| disk_used_bytes | int |  |
| disk_total_bytes | int |  |
| gpu_count | int | Detected GPU count (0 means no GPU) |
| gpu_utilization_percent | List[float] | GPU load for each card (length = gpu_count) |
| gpu_memory_percent | List[float] | GPU memory usage for each card |
| gpu_memory_used_mb | List[float] | GPU memory used in MB for each card |
| net_io_recv_bytes_per_sec | float | Average rate over past interval seconds |
| net_io_send_bytes_per_sec | float |  |
| process_count | int | Total current PID child processes (main process + child processes only) |
| open_fds_count | int | Number of open file descriptors for current process |
| uptime_seconds | float | Process uptime in seconds |

2. **`HealthStatus(BaseModel)`** (Sub-service health status, reused by /health):
| Field Name | Type | Description |
|---|---|---|
| service_name | str | "router"/"inference"/"pipeline"/"monitor"/"alert"/"cache"/ etc. |
| status | str | "healthy" / "degraded" / "unhealthy" |
| message | str | Detailed information (e.g. "ClickHouse OK, Kafka producer disabled") |
| last_check_at | datetime | UTC |
| metadata | Dict[str, Any] | Optional extra fields (default {}) |

**B. Class & Methods: `SystemResourceCollector(config: Dict[str, Any])`**
  - Attributes: `self.enabled`, `self.interval_sec` (default 15, from `monitoring.resource_collector.interval_sec`), `self.snapshot: Optional[ResourceSnapshot]`, `self._running: bool`, `self._task`, `_process_start_time`, `_last_net_io` (previous round net_io_counters);
  - `async initialize()`: try import psutil/GPUtil; on failure set enabled=False + log info + **do not raise exception**;
  - `async start()`: `asyncio.create_task(self._collect_loop())`;
  - `async _collect_loop()`: while self.running → `_collect_once()` → `asyncio.sleep(interval_sec)`;
  - `_collect_once() -> ResourceSnapshot`: actually collects all fields, internally wrapping each sub-item in try/except (any item failure fills 0, must not interrupt overall collection);
  - `get_latest_snapshot() -> ResourceSnapshot`: returns the most recent snapshot; if not yet collected, returns an "empty snapshot" with CPU=-1, Memory=-1, but with all fields complete;
  - `async stop()`: self.running = False; await task.

**New Configuration Items (monitoring.resource_collector section)**:
```yaml
monitoring:
  enabled: false
  alert_enabled: true
  resource_collector:
    enabled: true
    interval_sec: 15
    disk_path: /                     # df root partition
    net_iface: null                  # null means sum of all interfaces
    gpu_enabled: true                # GPU switch; when false, skips importing GPUtil
```

**Implementation Key Points**:
1. **CPU Collection**: `psutil.cpu_percent(interval=0.1)` (non-blocking single sample, smooths naturally over subsequent loops);
2. **Memory Collection**: `psutil.virtual_memory()` → percent/used/total;
3. **Disk Collection**: `psutil.disk_usage(disk_path)` → percent/used/total;
4. **GPU Collection** (Optional):
   ```python
   try:
       import GPUtil as GPU
       gpus = GPU.getGPUs()
   except Exception:
       gpus = []
   ```
   gpu_utilization_percent = [gpu.load*100 for gpu in gpus]; returns `gpu_count=0` and empty lists when GPU is unavailable;
5. **Network IO Rate**:
   - Each round records `now = psutil.net_io_counters()` (delta of bytes_recv/bytes_sent from previous round ÷ elapsed seconds); first round fills 0;
6. **Process-level Collection**: Current process `psutil.Process(os.getpid())` → `len(p.children(recursive=True))` as process_count; under Linux/Mac `.num_fds()` as open_fds;
7. **Uptime**: `time.time() - _process_start_time`;
8. **RESOURCE_METRICS Instrumentation**: Writes to the following Gauges at the end of each `_collect_once` round (defined in Task 3.2):
   - `RESOURCE_METRICS.cpu_percent.set(s.cpu_percent)`
   - `RESOURCE_METRICS.memory_percent.set(s.memory_percent)` / `memory_used_bytes` / `memory_total_bytes`
   - `RESOURCE_METRICS.disk_percent` / `disk_used_bytes` / `disk_total_bytes`
   - `RESOURCE_METRICS.gpu_count.set(gpu_count)` / `gpu_utilization_percent.labels(gpu_id=i).set(...)`
   - `RESOURCE_METRICS.net_recv_bytes_per_sec` / `net_send_bytes_per_sec`
   - `RESOURCE_METRICS.process_count` / `open_fds`
   - `RESOURCE_METRICS.uptime_seconds`
9. **Exception Fallback**: Any collector step raising Exception → `logger.warning("Resource collector item failed: %s", e)`, field filled with 0, **loop not stopped**.

**Core Constraints**:
- `_collect_loop` must be `async`, utilizing `asyncio.sleep` to avoid blocking the event loop;
- When `monitoring.enabled=False`, main.py **does not instantiate** SystemResourceCollector at all, producing zero psutil calls;
- GPU must not be a strict dependency (all functions operate normally without GPU);
- `get_latest_snapshot()` returns an object with complete fields; consumers (/status / analytics) require no null checks for AttributeError.

**monitoring/alert_rules.yml (4 default alert rules, strictly matching built-in AlertManager rules for dual-track compatibility)**:
```yaml
groups:
  - name: llm-router.rules
    rules:
      - alert: HighErrorRate
        expr: |
          sum by (service) (rate(
            {__name__=~"llm_router_inference_requests_total|inference_requests_total", status="error"}[5m]
          ))
          /
          sum by (service) (rate(
            {__name__=~"llm_router_inference_requests_total|inference_requests_total"}[5m]
          ))
          > 0.05
        for: 2m
        labels:
          severity: critical
          team: llm-platform
        annotations:
          summary: "High error rate (>5%)"
          description: "service {{ $labels.service }} error rate {{ $value | humanizePercentage }}"

      - alert: HighLatencyP95
        expr: histogram_quantile(0.95, sum by (le,model_name) (rate(inference_request_duration_seconds_bucket[5m]))) > 5
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "P95 latency > 5s per model"
          description: "model {{ $labels.model_name }} p95={{ $value }}s"

      - alert: HighMemoryUsage
        expr: process_resident_memory_bytes / on (job) group_left() machine_memory_bytes > 0.9
              or llm_router_memory_percent > 90
        for: 2m
        labels: { severity: warning }
        annotations: { summary: "Memory usage > 90%" }

      - alert: HighDiskUsage
        expr: llm_router_disk_percent > 80
        for: 5m
        labels: { severity: warning }
        annotations: { summary: "Disk usage > 80%" }

      - alert: PipelineDLQAccumulating
        expr: increase(llm_router_dead_letter_total[10m]) > 10
        for: 3m
        labels: { severity: critical }
        annotations: { summary: "Pipeline dead-letter accumulating" }
```

### Task 3.5: Alert Manager AlertManager (Built-in Python Implementation, Dual-track Optional)

**File**: `src/llm_router_part4_monitor.py` (Following Task 3.1 Schemas and SystemResourceCollector)

**A. New Pydantic Models (Same file)**:

1. **`AlertRule(BaseModel)`**:
| Field | Type | Description |
|---|---|---|
| name | str | Unique identifier, e.g. "HighErrorRate" |
| expr_lambda_src | str | Reserved; actually uses condition method |
| threshold | float | Threshold (5% → 0.05, 90% → 90) |
| duration_seconds | int | Duration window for deduplication |
| severity | str | "info" / "warning" / "critical" |
| description | str | Human-readable description |
| enabled | bool | Switch |
| extra_labels | Dict[str, str] | Default {} |

2. **`AlertRecord(BaseModel)`**:
| Field | Type |
|---|---|
| alert_id | UUID |
| rule_name | str |
| severity | str |
| status | str | "firing" / "resolved" |
| value | float |
| threshold | float |
| fired_at | datetime |
| resolved_at | Optional[datetime] |
| description | str |
| labels | Dict[str, str] |

**B. Class: `AlertManager(config: Dict, services_ref: Dict[str, Any])`**
  - Attributes: `self.enabled`, `self.rules: List[AlertRule]`, `self._active: Dict[str, AlertRecord]` (key=rule_name), `self._history: List[AlertRecord]` (ring buffer max 1000), `self._notifiers: Dict[str, BaseNotifier]`, `self._running: bool`, `self._task`, `self._interval_sec`;
  - `async initialize()`:
    1. Load 4 default rules (see table below);
    2. Load 3 reserved Notifier implementations for Slack/Email/PagerDuty (defaults to printing stdout and returning success; if webhook exists in config, performs HTTP POST);
  - `_load_default_rules() -> List[AlertRule]` static return:

| name | threshold | duration_seconds | severity | Evaluation Condition (How value is extracted from metrics/snapshot) |
|---|---|---|---|---|
| HighErrorRate | 0.05 | 120 | critical | `inference_requests_total{status="error"} 5m rate / total > 0.05` |
| HighLatencyP95Sec | 5.0 | 300 | warning | Histogram P95 (Internal approximation allowed: take p95 / 1000 of recent N inference latency_ms entries > 5) |
| HighMemoryPercent | 90.0 | 120 | warning | latest_snapshot.memory_percent > 90 |
| HighDiskPercent | 80.0 | 300 | warning | latest_snapshot.disk_percent > 80 |
| (Optional) PipelineDLQ | 10 | 180 | critical | `dead_letter_total` increase over 10m window > 10 |

  - Method: `async start()` → `create_task(self._eval_loop())`;
  - Method: `async _eval_loop()`: while running → for each enabled rule call `_evaluate_rule(rule)` → produce firing/resolved events → `_record_event` + `_notify_all` → `sleep(interval_sec)`;
  - Method: `_evaluate_rule(rule: AlertRule) -> Tuple[bool, float]` → (is_triggered, current_value);
    - HighErrorRate: Internal sliding window counter (INFERENCE_METRICS instrumented in inference layer); P4 allows approximation via `SYSTEM_METRICS.errors_total` / total;
    - HighLatencyP95Sec: Read recent 5-minute latencies directly (can append to deque(maxlen=1000) inside InferenceEngine and take quantile; if not exposed in P2/P3, fall back to Prometheus instant query calling `http://localhost:9090/api/v1/query`; on failure, fallback to "no data, do not trigger");
    - Memory/Disk: Read `resource_collector.get_latest_snapshot().memory_percent / disk_percent` directly;
  - Method: `_record_event(rule, firing: bool, value, labels)`:
    - firing and hitting condition continuously N times within duration → set to active; otherwise pending;
    - active and missing condition continuously N times within duration → set to resolved;
    - Record event into history (append, `pop(0)` if over 1000, or use `collections.deque(maxlen=1000)`);
    - `ALERT_METRICS.alerts_total.labels(rule, severity, action=firing|resolved|deduplicated).inc()`;
  - Method: `_notify_all(record: AlertRecord, action: str)`: Iterate self._notifiers.values() → `await notifier.send_alert(record, action)` (wrapped in try/except, failure of one notifier does not affect others); `ALERT_METRICS.notifications_total.labels(channel=name, status=ok|fail).inc()`;
  - Method: `get_active_alerts() -> List[AlertRecord]` (status=firing, dict friendly);
  - Method: `get_history(limit=200) -> List[AlertRecord]` (reverse order by fired_at);
  - Method: `async stop()`.

**C. Reserved Notifier Abstraction (Same file)**:
- Abstract Base Class `BaseNotifier(ABC)`: `async send_alert(record, action) -> bool`
- `StdoutNotifier(BaseNotifier)`: Always enabled by default, prints alert to logger.info
- `SlackWebhookNotifier(BaseNotifier)`: Enabled only when config `monitoring.notifiers.slack.webhook_url` is non-empty; POST JSON `{"text": ":red_circle: [FIRING] HighErrorRate ..."}`; skips if webhook_url is empty; HTTP failure outputs logger.warning without throwing;
- `EmailNotifier` / `PagerDutyNotifier`: P4 writes empty classes + pass (send_alert always returns True, no real transmission); keep config keys commented in README for P7 implementation.

**New Configuration Items (Appended under monitoring section)**:
```yaml

  alert_enabled: true
  alert_manager:
    eval_interval_sec: 15
    rules_override: []               # Allows overriding default rules (empty list uses 4 built-in rules)
    suppress_duplicate_seconds: 300  # Suppresses duplicate notifications for same rule within N minutes
    history_max_size: 1000
    notifiers:
      stdout: { enabled: true }
      slack:
        enabled: false
        webhook_url_env: SLACK_ALERT_WEBHOOK_URL
        channel: "#alerts"
        mention: "@oncall"
      email: { enabled: false, smtp_host: "", smtp_port: 587, username_env: "", password_env: "", from_addr: "", to_addrs: [] }
      pagerduty: { enabled: false, routing_key_env: PAGERDUTY_ROUTING_KEY }
```

**Core Constraints**:
- Alert manager evaluation loop is async and non-blocking; single rule execution timeout ≤ 1s, longer queries run in background (HTTP query to Prometheus must enforce timeout=2s);
- `monitoring.enabled=False` → Not instantiated; `monitoring.enabled=True` and `alert_enabled=False` → Instantiated but `_eval_loop` does not start (empty shell, get_active returns empty list);
- Deduplication: Requires "hitting condition continuously for duration_seconds / eval_interval_sec times" to trigger firing, avoiding false positives from single spikes; resolved logic operates identically;
- History records strictly limited to max size 1000 to prevent memory leaks.
